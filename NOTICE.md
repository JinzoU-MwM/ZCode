# ZCode Feature Notice and Third-Party Component Declaration

> English translation. The Chinese edition, [NOTICE.zh-CN.md](NOTICE.zh-CN.md), is the original text.

This notice applies to the source code published in this repository and its build outputs. Features, permissions, storage locations and network behaviour differ between the runtime forms; the default settings of one form must not be read as unified settings for the whole project.

## 1. AI Output, Execution Permissions and Automation Risk

AI-generated code, commands, explanations, files and suggestions may contain errors, omissions, security defects or third-party rights issues. They should be checked against the actual files, command exit statuses, tool results and tests; a model's claim that something is "done", "handled safely" or "authorized" does not constitute proof of fact or of authorization. Before important operations, review the execution target, the recipients and the impact, and keep a recoverable backup.

File, terminal, Git and Agent tools and external processes can read and write files, start processes and access the network within the permissions of the operating-system account that actually runs them. In a Web or remote workspace, operations may take place on the server side, on an SSH host, in WSL or in a container environment; the execution location cannot be inferred solely from the device on which the current page is displayed. The current shared Agent execution adapter provides no default operating-system sandbox; the working directory, workspace identity, Git worktree, browser page isolation and the run context of the Node REPL must not be treated as a system-level isolation guarantee for all tools.

The shared run configuration uses the `build` permission mode by default; when the standalone CLI runs a non-interactive task via `--prompt` and `--mode` is not specified, it uses `yolo`. Interactive sessions, desktop sessions, resumed tasks and hosts may use their own configured, saved or passed-in modes. Whether each step is confirmed individually depends on tool declarations, permission rules and the run mode; `yolo` without the read-only planning constraint also enabled lets ordinary tool operations through, while interactive tools and tools that explicitly require confirmation still have their own rules. Model tool approval is not a unified permission switch for the whole application, and it cannot be assumed on that basis that terminal operations, plugin processes or update downloads all pass through the same approval flow. See [CLI prompt mode](apps/zcode-cli/packages/cli/src/run.ts#L486) and [tool permission decision](apps/zcode-cli/packages/core/src/permission/service.ts#L97).

## 3. Local Data, Logs and Credentials

Data may be stored separately on the desktop device, in the browser, on the host running the CLI, in SSH/WSL environments and in external services. The desktop and server data directories can be affected by the run environment and launch configuration and contain settings, sessions, attachments, caches, task records, plugins and logs; the standalone CLI's default session database is located at `~/.zcode/cli/db/db.sqlite`. Closing the window, logging out, uninstalling the client or deleting a workspace should not be understood as having cleared all copies in other environments, separate data directories, backups and external services.

The memory feature's defaults and entry points differ: the standalone CLI's default configuration enables memory, while the desktop application setting is off by default. Once enabled, it may analyse saved sessions, persist memories and reuse them in later tasks; the related extraction or consolidation may produce additional model requests. Automation plans, run records and unfinished tasks also have their own persistence locations; restoring these records does not guarantee that earlier external operations were undone or can be fully replayed.

The shared Agent's model input/output logs are written locally by default in development and production runs, except in the test environment. The logs may contain prompts, code, context, tool arguments and model replies; request headers and some image and video data are redacted, but it cannot be assumed that all user text has been redacted. Production has rotation and trimming by default; explicitly enabling full retention changes that behaviour. The desktop main process, Host, scheduler, Web service and remote daemon also have their own logs and crash records; a single log's limit does not represent a project-wide uniform retention period.

Credential storage mechanisms also differ: the CLI shared credential file uses an encryption mechanism whose default key can be derived from local machine environment information, and its read logic also accepts plaintext records; the desktop/Node service's credentials likewise use a local encrypted file with a configurable or environment-derived key, not the system keychain; Web OAuth credentials may be stored in localStorage. Model configuration, environment variables, plugin/MCP settings, SSH configuration and remotely synchronized data may also contain valid credentials; these stores should not be uniformly treated as a system keychain, hardware isolation or a guarantee that data "never leaves the machine".

The embedded browser uses persistent browsing data; explicitly importing Cookies and LocalStorage from another browser can give it the corresponding login state. Clearing the cache and clearing all site data are different operations, and browser records, downloaded files, web page recordings and model logs are not necessarily deleted by the same cleanup entry point. Do not write real keys or tokens into files tracked by version control. Before copying logs, uploading feedback, sharing conversations or backing up the data directory, check the receiving scope to avoid committing real credentials, raw sessions and private project content to public repositories or issue reports.
